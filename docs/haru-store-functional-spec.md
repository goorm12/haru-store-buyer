# 하루상점 — 1차 MVP 상세 기능 명세서

- 버전: v1.0
- 작성일: 2026-10-14
- 서비스명: 하루상점 / Haru Store
- 기준: [요구사항 최종본](./haru-store-requirements.md), [용어 정의](./haru-store-glossary.md)
- 범위: 현장 결제 + 픽업
- 목적: 화면 설계, 프론트엔드·백엔드 구현, 기능 검수의 공통 기준

## 1. 문서 적용 기준

P01~P16은 확정 정책이다. 이 문서는 그 정책을 기능과 검수 조건으로 구체화한다. 원문에 없는 길이·파일 크기·정렬·내부 코드 등은 **구현 기본안**이며 사업 정책의 추가 확정을 의미하지 않는다. 원문에서 별도 설계 대상으로 남긴 일정·장소 변경은 보수적인 구현안과 후속 작업을 구분해 기술한다. 원본 요구사항은 수정하지 않는다.

온라인 결제·배송·환불·정산, 직원 초대, 쿠폰, 상품 옵션, 리뷰, 장바구니, 지점 간 재고 공유, 여러 상점 상품 일괄 등록은 제외한다. 최소 모집 인원 달성 조건도 없다.

## 2. 역할·사용 환경·권한

| 역할 | 사용 환경 | 허용 범위 |
| --- | --- | --- |
| 비회원 | 구매자 앱 | 공개 상점·공구 상품 조회 |
| 구매자 | Capacitor 앱 | 본인 정보·저장 상점·예약·알림·신고 관리 |
| 판매자 | PC·모바일 반응형 웹 | 본인 소유 상점과 그 상점의 공구·예약 관리 |
| 플랫폼 운영자 | 운영 웹 화면 | 신고 조회, 상품 숨김, 상점 제한·해제, 조치 이력 |

- 구매자·판매자는 같은 카카오 계정과 회원 시스템을 사용한다. 상점 최초 등록 성공 시 판매자 역할을 부여한다.
- 구매자와 판매자 역할을 함께 가질 수 있다. 역할별 화면 진입만으로 서버 권한이 부여되지 않는다.
- 운영자 권한은 일반 회원이 선택하거나 상점 등록으로 얻을 수 없다. 운영 권한 부여 방식은 기술·운영 설정으로 관리한다.
- 서버는 모든 요청의 회원, 대상 예약 소유권, 대상 상점 소유권을 검증한다. 화면에서 넘긴 sellerId·buyerId만 신뢰하지 않는다.
- 판매자 상점 전환은 조회 범위 선택이다. 다른 판매자의 storeId를 보내도 조회·변경할 수 없다.
- 운영자 외에는 신고자의 정보나 다른 판매자의 예약 명단을 조회할 수 없다.

DB 스키마를 확정하는 표가 아니다. 화면과 처리에 필요한 논리 정보다. 공구 게시물과 독립 상품 카탈로그 분리는 필수가 아니다.

### 4.2 구현 기본안

| 입력 | 기본 검증안 |
| --- | --- |
| 이름 | 공백 제외 필수, 앞뒤 공백 제거, 1~50자 |
| 상점명·상품명 | 필수, 1~100자 |
| 연락처 | 직접 입력, 공백·하이픈 정규화 후 전화번호 형식 검증. 인증 완료 표시 금지 |
| 주소 | 도로명 또는 지번 주소·상세주소. 주소 선택 도구 미정, 직접 입력 가능 |
| 가격 | 원화 정수, 1원 이상. 부동소수 계산 사용 금지 |
| 총 수량·예약 수량 | 1 이상 정수 |
| 1인 최대 수량 | 미설정(null) 또는 1 이상 정수. 미설정은 개인 한도만 없음 |
| 이미지 | 대표 1장 필수, 상세 선택. 기본안 JPEG·PNG·WebP, 파일당 10MB 이하, 상세 10장 이하 |
| 상세 설명 | 필수, 기본안 1~10,000자. 임의 스크립트 실행 불가 |
| 사유·신고 내용 | 공백 제외 필수, 기본안 1~1,000자 |
| 운영시간 | 시작 < 종료, 기본안 동일 날짜 내 시간. 자정 넘김 운영은 별도 설계 |

- 프론트엔드와 서버가 같은 검증을 수행하되 서버 판단이 최종이다.
- 작성 중 저장은 필수 항목 미완성도 허용할 수 있지만 공개 시 모든 필수 조건을 검증한다.
- 업로드 실패 시 이미 저장된 내용·이미지를 잃지 않는다. 서버에서 형식·크기도 재검증한다.
- 오류는 해당 입력 옆에 표시하고 수정 가능하게 한다. 내부 식별자나 서버 오류 전문을 노출하지 않는다.

## 5. 회원 기능

### AUTH-01 카카오 로그인·가입 — B01/S01, P02·P15

**입력:** 카카오 로그인 결과, 최초 필수 동의, 이름·연락처.

**흐름:** 로그인 시작 → 카카오 인증 → 서버 검증 → 기존 회원 조회 → 신규 회원이면 필수 정보·동의 → 서비스 세션 발급 → 원래 요청 화면으로 복귀.

- 카카오 로그인 취소·실패 시 예약 생성이나 가입 완료로 처리하지 않는다.
- 기존 회원이면 새 계정을 중복 생성하지 않는다. 필수 프로필이 없으면 보완 화면으로 이동한다.
- 이메일·전화번호를 카카오에서 항상 받는다고 가정하지 않는다. 연락처는 직접 입력한다.
- 필수 동의 문구·버전·시각을 저장한다. 선택 동의는 필수 가입과 분리한다.
- 비회원이 예약·저장·신고를 선택하면 로그인 후 같은 대상 화면으로 돌아간다.
- 구매자 앱에 판매자 관리 모드를 구현하지 않는다. 판매자 웹에서 같은 계정으로 로그인할 수 있다.

**검수:** 같은 계정의 앱·웹 로그인은 같은 회원으로 연결되고, 로그인 실패 후 예약이 생기지 않는다.

### AUTH-02 프로필 수정·로그아웃 — B11

- 이름·연락처 수정 시 형식을 검증하고 저장 결과를 표시한다.
- 새 예약에 최신 프로필을 사용한다. 기존 예약의 예약자 스냅샷을 일괄 바꾸지 않는다.
- 로그아웃 시 해당 세션을 종료하고 기기의 회원 푸시 연결을 해제한다. 다른 기기 로그아웃 여부는 세션 설계 사항이다.
- 세션 만료 시 로그인 안내 후 원래 화면으로 복귀하고 변경 요청을 자동 중복 실행하지 않는다.

**검수:** 로그아웃한 기기에서 개인정보 API 접근이 거절되고 다른 사용자로 로그인해 이전 예약을 볼 수 없다.

## 6. 상점 기능

### STORE-01 상점 검색·조회 — B02/B05

- 비회원도 상점명으로 검색하고 상점명·주소·소개·픽업 운영시간·연락처를 조회한다.
- 검색 결과 없는 경우 검색어 수정 안내, 오류인 경우 재시도 제공. 결과 없음과 통신 실패를 구분한다.
- 정상 상점과 공개 상품만 일반 검색에 노출하는 기본안을 사용한다.
- 제한·폐점 상점의 기존 예약자는 예약 상세에서 당시 픽업·문의 정보를 계속 확인한다. 정상 판매 중처럼 표시하지 않는다.

**검수:** 제한 상점은 신규 예약할 수 없지만 기존 예약의 안내가 사라지지 않는다.

### STORE-02 저장·기본 상점 — B03, P03

- 로그인 회원만 저장·해제 가능. 같은 상점을 중복 저장하지 않는다.
- 기본 상점은 저장한 정상 상점 중 구매자가 직접 지정한다. 한 회원에 최대 1개다.
- 최초 저장만으로 자동 기본 지정하지 않는 구현안을 사용하고 지정 버튼을 제공한다.
- 앱 진입 시 기본 상점 유효성 확인 → 유효하면 해당 상품 목록, 없으면 상점 선택 화면.
- 기본 상점 저장 해제·폐점·접근 제한 시 기본 지정을 해제하고 재선택을 안내한다. 임의 대체하지 않는다.
- 다른 상점을 구경해도 기본 상점이 자동 변경되지 않는다.

**검수:** 일반 상점 전환과 기본 상점 변경이 구분되고, 기본 지정은 서버에서도 1개로 유지된다.

### STORE-03 판매자 상점 개설 — S02, P01

**필수:** 상점명, 픽업 주소, 연락처, 픽업 운영시간. 소개는 입력 지원.

- 로그인 → 정보 입력 → 검증 → 즉시 개설 → 소유권 연결·판매자 역할 부여 → 운영 홈.
- 사업자·연락처 인증 완료라고 표시하지 않는다. 사전 운영자 승인 단계 없음.
- 한 판매자가 여러 상점을 추가 가능. 다른 상점의 수량·상품·예약을 복사하거나 공유하지 않는다.
- 같은 요청 재시도로 상점이 중복 생성되지 않도록 처리한다.

**검수:** 운영 승인 대기 없이 개설되고, 다른 판매자는 신규 상점에 접근할 수 없다.

### STORE-04 운영 상점 전환·설정 — S01/S02

- 상점 하나이면 바로 운영 홈. 여러 개이면 마지막으로 접근 가능한 소유 상점으로 진입.
- 이전 상점 권한이 없어졌으면 운영 상점 목록으로 이동한다.
- 전환 시 목록·통계·검색 조건의 상점 범위를 갱신한다. 저장되지 않은 편집은 이탈 확인 제공.
- 상점 주소·운영시간 변경은 신규 공구 기본값에 적용한다. 기존 예약의 약속은 유지하며 LIST-03 절차로 변경한다.
- 상점 임의 삭제·폐점 버튼은 원문에 없는 기능이므로 본 명세에서 추가하지 않는다. 제한·탈퇴에 따른 접근 불가를 처리한다.

## 7. 공구 상품 기능

### LIST-01 목록·상세 조회 — B04/B05/S04

**구매자 표시:** 대표 이미지, 상품명, 판매 단위, 원화 단가, 접수 상태, 1인 한도, 예약 마감, 픽업 가능 날짜·운영시간·장소, 직접 취소 제한과 마감.

- 판매자 목록은 작성 중 포함, 구매자는 공개 상품만 조회한다.
- 신규 예약 가능 → ‘예약하기’. 유효 예약 있음 → ‘내 예약 보기’ 및 변경 안내. 픽업 완료 이력 있음 → 같은 공구 재구매 불가 안내.
- 작성 중·숨김·취소·제한·마감·품절은 신규 예약 금지. 기존 예약의 접근은 유지한다.
- 품절은 남은 수량 0 표시이며 새로운 공구 상태를 만들지 않는다.
- 기본 목록은 최신 공개 순, 페이지 단위 조회를 구현 기본안으로 사용한다.

**검수:** 목록에서 접수 가능했어도 상세·확정 시 최신 상태를 재검증한다.

### LIST-02 작성·공개 — S05, P05·P07

**입력:** 공구 등록 정보 4.1·4.2 참조. 취소 제한 기본값은 꺼짐, 개인 한도는 미설정을 구현 기본안으로 사용한다.

- 작성 중 저장과 공개를 구분한다. 공개 시 예약 시작·마감, 1개 이상의 픽업일, 운영시간·당일 접수 마감을 검증한다.
- 예약 시작 < 예약 마감. 픽업일은 오늘 이상, 서로 중복 없음. 설정한 조건으로 예약 가능한 날짜가 최소 하나 있어야 한다.
- 당일 접수 마감은 해당 픽업 운영 종료보다 늦을 수 없는 기본안을 적용한다. 전체 예약 마감과 독립적으로 검사한다.
- 미래 시작 → 예약 예정, 현재 접수 기간 → 예약 중, 기간 종료 → 마감. 경계는 11장 참조.
- 하나의 공구는 하나의 상점에 소속. 공개 후 다른 상점으로 이동시키지 않는다.

**검수:** 15시 마감은 고정값이 아니며 판매자가 설정한 값으로 동작한다. 오늘 픽업이 이미 마감됐어도 미래 픽업 날짜가 가능하면 공개할 수 있다.

### LIST-03 기존 공구 수정 — S05, P11

| 변경 항목 | 처리 |
| --- | --- |
| 이미지·설명·상품명 | 수정 가능, 이력 보존. 기존 예약의 상품 식별·확인 정보 유지 |
| 단가 | 신규 예약에 적용. 기존 예약의 수량 증가·감소에도 예약 당시 단가 유지 |
| 총 수량 | 점유 수량 이상만 가능. 동시에 예약이 들어와도 원자적으로 검증 |
| 1인 한도 | 신규 예약·수량 증가에 적용. 기존 수량이 새 한도보다 많아도 자동 감소하지 않음 |
| 직접 취소 제한 | 신규 예약에 적용. 기존 예약 정책 스냅샷 변경 금지 |
| 예약 마감·당일 마감 | 미래 접수·수량 증가 조건 갱신. 기존 예약을 자동 취소하지 않음 |
| 기존 예약이 없는 픽업일 | 추가·수정·삭제 가능, 유효성 재검증 |
| 예약이 있는 날짜·장소·운영시간 | 기존 약속 자동 덮어쓰기 금지. 별도 처리·안내 후 변경 |
| 판매 단위·실제 상품 구성 | 기존 계약 의미가 달라지는 변경은 기본안에서 차단하고 새 공구 등록 안내 |

**일정·장소 변경 구현 기본안:** 영향 예약 목록·수량 표시 → 원래 약속 이행 가능 여부 확인 → 이행 가능하면 기존 예약 스냅샷 유지하고 신규 예약 조건만 변경 → 이행 불가하면 접수 중단, 구매자에게 사유 안내 및 합의된 처리 진행. 미해결 예약을 다른 날짜·장소로 일괄 이동하지 않는다.

자동 변경 동의·대체 날짜 제안 화면은 원문에서 후속 설계 대상으로 남아 있다. MVP 기본안은 기존 약속 유지 또는 사유 있는 판매자 취소를 통해 처리하며, 요구사항 정책을 임의 변경하지 않는다.

**검수:** 총 20개 중 12개 점유 시 11개로 축소 실패. 기존 단가 10,000원 예약에 신규 가격 12,000원이 소급되지 않는다.

### LIST-04 접수 중단·재개 — S06

- 접수 중단은 신규 예약·수량 증가 차단. 기존 예약·픽업·허용된 감소·취소·날짜 변경 유지.
- 재개 시 기간·공구 취소 여부·숨김·상점 제한을 검증한다. 운영자 제한을 판매자가 해제할 수 없다.
- 마감·품절이어도 기한이 남고 수정이 허용되면 접수 조건을 고칠 수 있으나 자동 예약 취소 없음.

### LIST-05 공구 전체 취소 — S06

- 권한 확인 → 취소 사유 → 영향 예약 수·수량 표시 → 확인 → 공구 취소 및 유효 예약 판매자 취소 → 수량 반환·이력·알림.
- 취소·픽업 완료·미수령 예약은 그대로 유지하는 구현안을 적용한다. 이들은 유효 예약 정의에 포함되지 않는다.
- 처리 중 신규 예약·변경·픽업을 같은 상태 버전 기준으로 차단하여 일부만 취소되는 경쟁을 방지한다.
- 중복 실행 시 수량이 두 번 반환되거나 알림이 두 번 생성되지 않는다.
- 예약이 있는 공구는 삭제하지 않는다. 작성 중 삭제 기능은 별도 요청 없이 추가하지 않는다.

## 8. 구매자 예약 기능

### RSV-01 예약 생성 — B06/B07, P04~P08

**입력:** 공구 ID, 정수 수량, 픽업일. 예약자 이름·연락처는 프로필에서 확인한다.

**사전 표시:** 판매 단위·단가·예상 금액, 상점·주소·픽업 시간, 개인 한도, 취소 제한, 변경·취소 마감. 당일 예약이면 ‘오늘 예약은 변경·직접 취소할 수 없습니다’ 안내.

**서버 처리:**

1. 세션·회원 이용 상태 확인.
2. 공구·상점 접근 상태, 공개 여부, 취소·접수 중단 여부 확인.
3. 같은 구매자·공구의 유효 예약 및 픽업 완료 이력 확인.
4. 전체 접수 기간과 선택 픽업일·당일 마감 확인.
5. 수량·전체 잔여·취소 제외 개인 한도 검증.
6. 최신 단가·정책으로 요청 전 표시와 차이가 있으면 갱신 후 구매자 재확인 요구.
7. 원자적으로 수량 확보와 예약 생성. 예약 확정·미결제 저장.
8. 예약번호·스냅샷·이력·알림 이벤트 저장 후 성공 응답.

- 성공 즉시 확정, 판매자 승인 없음. 실패 시 수량만 점유되거나 예약만 생성되는 부분 성공 금지.
- 화면상 금액 계산만 믿지 않는다. 서버가 정수 단가×수량 계산.
- 유효 예약 있음 → 기존 예약 화면. 취소 후 재예약은 새 예약번호로 생성하고 취소 이력 유지.
- 픽업 완료 후 같은 공구는 재예약 불가. 다음 공구는 별개다.
- 무제한 개인 한도도 전체 잔여보다 많이 예약할 수 없다.

**결과 화면:** 예약번호, 상품·단위·수량·금액, 픽업일·장소·운영시간, 현장 결제 안내, 내 예약 이동.

### RSV-02 내 예약 목록·상세 — B08/B09

- 본인 예약만 조회. 예정은 예약 확정, 지난 내역은 취소·픽업 완료·미수령을 기본 분류로 사용한다.
- 날짜가 지났어도 예약 확정이면 ‘픽업일 경과’ 표시로 남기고 자동 미수령 처리하지 않는다.
- 현재 공구 정보보다 예약 당시 단가·정책·약속 정보를 우선 보여준다. 변경 공지가 있으면 함께 표시.
- 제한·숨김 상품도 본인 예약 상세 접근과 연락처·요청 경로 유지.
- 변경·취소 버튼 활성 여부는 서버가 반환한 허용 행동·사유로 표시하고 실행 시 다시 검증한다.

### RSV-03 수량 증가·감소 — B09

| 행동 | 조건 |
| --- | --- |
| 증가 | 예약 확정, 기존 픽업일 전날 마감 전, 신규 접수 열림, 잔여·개인 한도 충족 |
| 감소 | 예약 확정, 기존 픽업일 전날 마감 전, 직접 취소 제한 없음, 결과 수량 ≥ 1 |

- 감소는 공구 접수 중단·마감 후에도 허용된다. 직접 취소 제한이 있으면 감소 버튼도 차단한다.
- 증가 수량만큼 점유를 늘리고 감소분은 반환한다. 금액은 예약 당시 단가 기준이다.
- 차액을 온라인 청구·환불하지 않는다. 현장 결제 예정 금액만 변경한다.
- 같은 수량 저장은 변경 없음으로 처리, 중복 이력·알림 생성하지 않는 기본안.
- 동시에 판매자 취소·다른 수정 발생 시 버전 충돌 반환, 최신 예약 다시 조회. 실패하면 기존 예약 유지.

**검수:** 취소 제한 예약의 3→2 실패, 3→4는 기한·접수·한도 내 성공. 당일 모두 실패.

### RSV-04 픽업일 변경 — B09, P09

- 예약 확정이고 기존 픽업일과 새 픽업일이 모두 오늘보다 미래이며 기존 변경 기한 내여야 한다.
- 새 날짜는 공구가 유지하는 유효 픽업일이어야 한다. 신규 접수 마감과 별개로 허용한다.
- 접수 중단·마감은 날짜 변경만을 막는 이유가 아니다. 공구 취소·유효 날짜 삭제·예약 종료 상태는 차단한다.
- 수량·단가는 유지하고 새 픽업 스냅샷과 마감 기준·알림을 갱신한다. 직접 취소 제한 여부는 예약 당시 값을 유지한다.
- 날짜와 수량을 함께 저장하면 두 행동의 조건을 모두 만족해야 하며 전체 성공 또는 전체 실패로 처리한다.

### RSV-05 구매자 전체 취소 — B09

- 예약 확정·전날 마감 전·직접 취소 제한 없음 → 취소 확인 → 구매자 취소 → 수량 반환 → 이력·알림.
- 취소 후 복원 없음. 다시 접수 가능하면 새 예약으로 처리한다.
- 당일·취소 제한·종료 예약은 직접 취소 불가. 사유와 연락처·요청 경로 표시.
- 판매자 취소 및 법정 요청 처리는 구매자 직접 취소 제한과 구분한다.

### RSV-06 문의·법정 요청 — B09/B12/O03, P16

- 예약 관련 요청 유형, 요청 내용, 연락처·예약번호를 확인하고 접수한다.
- 접수는 예약 취소 승인이나 수량 반환을 의미하지 않는다. 예약 상태는 별도 승인·처리 시 변경한다.
- 판매자·운영자에게 해당 예약 범위에서 요청 조회·처리 사유 기록을 제공한다. 법정 권리 요청을 시간 경과만으로 자동 기각하지 않는다.
- 탈퇴 이후에는 로그인 필수 API 대신 운영 연락 경로를 안내한다. 본인 확인과 최소 정보 제공 절차는 출시 운영 설계에서 확정한다.

## 9. 판매자 예약·현장 처리

### SELL-01 운영 홈·예약 목록 — S03/S07

- 현재 상점만 조회. 날짜 기본값은 한국 시간 오늘.
- 상품별 준비 수량 = 선택 날짜의 예약 확정 수량 합계. 취소·완료·미수령은 준비 수량에서 제외한다.
- 오늘 픽업 예정 건수와 수량을 구분한다. 3박스 예약 1건은 건수 1·수량 3.
- 픽업 완료 건수·미수령·픽업일 경과를 구분하여 표시한다.
- 예약번호·이름·연락처 검색, 상품·날짜·상태 필터. 페이징 기본안 적용.
- 연락처는 예약 운영 목적으로만 표시하고 공개 상품 페이지에는 구매자 정보 노출 금지.

### SELL-02 개별 예약 취소 — S08, P10

- 본인 상점·예약 확정 대상 확인 → 사유 입력 → 확인 → 판매자 취소·수량 반환·이력·구매자 알림.
- 구매자 취소 제한·전날 마감은 판매자의 공급 불가 취소를 막지 않는다.
- 이미 취소·픽업 완료·미수령이면 거절. 오기록은 SELL-06으로 정정 후 별도 판단.
- 공구 전체를 취소하지 않고 해당 예약만 처리한다.

### SELL-03 현장 결제 기록 — S08

- 실제 결제 확인 후 미결제→현장 결제 완료 기록. PG 결제 실행 없음.
- 예약 확정인 대상에 기록하는 구현 기본안. 취소·미수령 대상 결제 완료 버튼은 비활성.
- 처리자·시각 저장. 중복 완료 요청은 추가 기록·금액 계산 없음.
- 결제 기록과 픽업 상태는 독립. 결제만 완료해도 예약은 예약 확정이다.

### SELL-04 픽업 완료 — S08

- 예약번호 또는 이름·연락처로 확인 → 현재 상품·수량·날짜·금액 표시 → 실제 전달 확인 → 픽업 완료.
- 기본안은 현장 결제 완료 확인 후 픽업 완료를 허용한다. 두 개의 상태 기록을 구분하고 현장 처리 화면에서 연속 수행한다.
- 예약 확정만 완료 가능. 취소·미수령은 차단한다.
- 다른 날짜·지연 픽업은 실제 상황 확인이 필요하므로 날짜 불일치 안내를 표시하며 자동 날짜 변경을 하지 않는다.
- 픽업 완료 수량은 총 점유에서 반환하지 않는다. 동일 구매자의 같은 공구 재구매를 차단한다.

### SELL-05 미수령 처리 — S08, P12

- 예약 확정이며 픽업 운영시간 종료 후 미수령 처리하는 기본안.
- 확인 후 미수령·처리자·시각 기록. 결제 상태 임의 변경 없음.
- 자동 예약 취소·수량 반환·보관 기한 종료·폐기는 수행하지 않는다.
- 늦은 수령은 원문에 확정된 별도 자동 정책이 없다. 이미 미수령 상태이면 일반 픽업 완료를 바로 수행하지 않고 운영 확인 절차를 거친다.

### SELL-06 픽업·결제 오기록 정정 — S08, P13

- 실제 오기록 확인 → 정정할 필드 선택 → 현재·수정 후 값·필수 사유 표시 → 확인 → 이력 포함 갱신.
- 기본 정정: 픽업 완료→예약 확정, 현장 결제 완료→미결제. 사유·처리자·전후 값·시각 필수.
- 예약 상태와 결제 상태 각각 정정. 취소 예약을 정정 버튼으로 복구하거나 수량을 바꾸지 않는다.
- 픽업 상태 되돌림은 실제 수령을 취소하는 기능이 아니며 신규 예약·수량 반환을 만들지 않는다.
- 과거 날짜로 되돌리면 픽업일 경과 표시. 과거 알림을 소급 발송하지 않는다.
- 실제 돈의 환불·재결제 없음. 다른 기기의 상태 버전과 충돌하면 최신 상태 확인 후 다시 처리.

## 11. 날짜·수량·상태 공통 규칙

### 11.1 시간 경계

- 표시·사업 정책 기준은 Asia/Seoul, 서버 검증 기준 시각 사용.
- 변경·직접 취소 허용: 현재 시각 < 기존 픽업일 00:00. ‘전날 23:59까지’는 23:59:59까지를 포함하고 당일 00:00부터 차단하는 구현 표현이다.
- 신규 접수 기본안: 시작 ≤ 현재 < 전체 예약 마감. 당일은 현재 < 해당 날짜 당일 접수 마감도 만족.
- 마감 시각에 도달한 요청은 실패. 화면을 마감 전에 열었어도 처리 시각이 마감 이후면 실패한다.
- 날짜 변경은 기존·새 픽업일 모두 오늘보다 미래. 접수 중단이더라도 유효 날짜로 변경 가능.

### 11.2 수량 산식

```text
총 점유 수량 = 예약 확정 + 픽업 완료 + 미수령 상태의 수량 합계
남은 수량 = 공구 총 수량 - 총 점유 수량
개인 한도 사용량 = 같은 구매자·공구의 취소되지 않은 수량 합계
준비 수량 = 선택한 픽업일의 예약 확정 수량 합계
예상 금액 = 예약 당시 정수 단가 × 예약 수량
```

- 취소만 점유 반환. 픽업·미수령은 판매 또는 확보된 수량이므로 반환 없음.
- 감소는 감소분 반환. 날짜 변경은 전체 점유 불변.
- 기존 예약 변경 시 기존 수량을 중복 합산하지 않는다.
- 미수령 후 재예약은 원문에 금지로 확정되지 않았으므로 기본안은 잔여·개인 누적 한도·접수 조건 내 허용하되 종료 이력 보존. 이 세부 적용은 구현 설계에서 확인한다.

### 11.4 공구·접근 상태

- 작성 중, 예약 예정, 예약 중, 접수 중단, 마감, 공구 취소는 공구 접수 상태.
- 숨김과 상점 이용 제한은 운영 접근 상태이며 별도 공구 상태로 혼용하지 않는다.
- 시간 마감·수동 중단·숨김·제한이 동시에 있어도 예약 허용 조건을 모두 충족해야 한다.
- 접수 재개는 운영 숨김·상점 제한을 해제하지 않는다.

## 12. 신고·플랫폼 운영

### OPS-01 상점·상품 신고 — B12/O01

- 로그인 구매자가 대상 상점 또는 공구, 유형·내용을 입력해 접수한다. 유형 기본안: 정보 오류, 부적절한 상품, 거래 문제, 기타.
- 같은 요청의 중복 제출 방지. 신고만으로 자동 상품 숨김·예약 취소 없음.
- 운영자는 대상·접수 시각·내용·처리 상태를 조회하고 사유를 기록한다. 신고자의 연락처를 판매자에게 자동 공개하지 않는다.
- 접수·검토·처리 완료는 신고 업무 상태이며 예약 상태와 구분한다.

### OPS-02 상품 숨김·상점 제한·해제 — O02

- 운영자 전용. 사유 입력 → 영향 확인 → 조치·이력 저장.
- 숨김 상품은 일반 노출·신규·증가 차단. 상점 제한도 신규·증가 차단.
- 기존 예약 자동 취소 없음. 판매자에게 유효 예약의 이행·취소·연락 처리를 제공한다.
- 해제 시 원래 접수 기간·수량·다른 제한 확인. 기간 지난 공구를 예약 중으로 강제 복구하지 않는다.
- 판매자는 제한을 자체 해제하거나 새 공개 설정으로 우회할 수 없다.

### OPS-03 거래 요청 처리 — O03

- 제한 취소·탈퇴·공급 불가 관련 요청을 예약별로 확인하고 처리 내용·사유 기록.
- 처리된 취소는 정당한 권한의 예약 상태 변경과 연결한다. 요청 완료 표시만으로 수량을 반환하지 않는다.
- 운영자가 판매자 취소를 대행할 권한 범위는 원문에서 구체화하지 않았으므로, 기본안은 판매자 처리 요청·조치 기록을 제공한다. 법정 요청 담당자의 개인정보 접근과 실행 권한은 출시 운영 설계 사항이다.

## 13. 탈퇴·정보 처리 — ACCOUNT-01, B11, P16

1. 탈퇴 진입 시 본인 유효 예약·운영 상점·미완료 거래 목록 조회.
2. 거래 없음 → 영향 설명·확인 → 계정 탈퇴.
3. 거래 있음 → 허용 취소 또는 판매자·운영자 처리 요청 안내.
4. 해결되지 않았어도 요청을 무기한 거절하지 않는다. 거래 정보의 적법한 최소 보관과 계정 접근 종료를 분리 처리.
5. 판매자 탈퇴 시 소유 상점 신규 접수 중단, 기존 예약 자동 취소 없음. 이행·사유 취소 처리 경로 마련.
6. 세션·토큰·기기 푸시 연결 종료, 불필요 프로필·저장 상점 정보 파기.
7. 보존 대상 기록을 목적·기한·접근 권한에 따라 분리 보관, 종료 시 파기.

- 모든 개인정보를 일괄 5년 보관하지 않는다. 요구사항 3.3·3.4의 공식 근거와 실제 사업 역할 검토 결과로 필드·기산일을 정한다.
- 탈퇴 전 미완료 거래가 있음을 알리고, 탈퇴 후 문의 경로·본인 확인 방식 제공. 탈퇴 후 기존 앱 푸시 발송 금지.
- 기술 기본안: 거래 식별용 내부 참조는 보존 필요성에 따라 유지할 수 있으나 로그인 자격·일반 프로필과 분리. 회원 API에서 탈퇴 사용자의 일반 프로필 조회 차단.
- 재가입 시 이전 탈퇴 계정·예약을 임의로 복구하거나 개인 한도 우회 허용으로 가정하지 않는다. 법적 보관 범위 안의 동일인 처리 방법은 후속 설계다.

| CANCELLATION_RESTRICTED | 취소·감소 제한 안내 |
| INVALID_PICKUP_DATE | 유효 날짜 재선택 |
| VERSION_CONFLICT | 최신 상태 재조회·재확인 |
| REQUEST_PENDING | 처리 여부 조회, 새 요청 중복 실행 금지 |

코드는 API 설계 권장안이다. 사용자에게 그대로 보여주지 않는다.

- 예약 생성·수량 수정·취소·공구 취소·픽업 정정은 원자적 처리. 두 기기에서 동일 대상 수정 시 낙관적 버전 검증 또는 동등한 잠금 적용.
- 동일 요청 키 재시도는 기존 결과를 반환한다. 다른 내용으로 같은 키 사용 시 충돌 처리.
- 응답 유실 시 요청 키로 결과 확인. 확인 없이 ‘실패’로 판단해 새 예약 만들지 않는다.
- 취소·감소의 수량 반환은 정확히 한 번. 알림 실패가 예약 실패로 보이지 않게 한다.
- 목록·통계는 최신 상태를 반영하며 중요한 동작 실행 시 서버에서 다시 검증한다.
- 실패 메시지·재시도·빈 화면을 구분하고 입력 내용을 가능한 한 유지한다.

## 18. 세부 설계 인계 항목

확정 사업 정책과 별도로 다음 작업을 수행한다. 본 문서의 구현 기본안을 수용하거나 조정한 결과는 버전 이력에 남긴다.

- 이미지·문자 길이 제한, 주소 도구, 운영시간 캘린더·휴무·자정 넘김 설계
- 운영자 접근·인증·신고 처리 화면과 탈퇴 후 본인 확인·문의 경로
- 예약 있는 일정·장소 변경의 합의·재선택 UI, 미수령 이후 늦은 수령·재가입 동일인 처리
- 회원·공구·예약·이력·알림 데이터 모델 및 API 상세
- 결제 확인 후 픽업 완료 조건, 미수령 시점, 오기록 정정 범위의 구현 기본안 확인
- 출시 전 보존 의무 주체·필드·기산일, 약관·개인정보 처리방침 적용
- 향후 결제 방식과 수령 방식을 별도 필드로 확장하되 MVP는 현장 결제+픽업만 허용
