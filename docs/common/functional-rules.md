# 하루상점 — 공통 기능 규칙

- v1.1 / 2026-10-14
- 원본 장 번호와 기능 ID 유지. 역할별 구현 명세는 각 저장소 문서를 참조한다.

## 1. 문서 적용 기준

P01~P16은 확정 정책이다. 이 문서는 그 정책을 기능과 검수 조건으로 구체화한다. 원문에 없는 길이·파일 크기·정렬·내부 코드 등은 **구현 기본안**이며 사업 정책의 추가 확정을 의미하지 않는다. 원문에서 별도 설계 대상으로 남긴 일정·장소 변경은 보수적인 구현안과 후속 작업을 구분해 기술한다. 역할별 화면은 별도 문서에서 관리하며 공통 정책과 구현 기본안을 구분한다.

온라인 결제·배송·환불·정산, 직원 초대, 쿠폰, 상품 옵션, 리뷰, 장바구니, 지점 간 재고 공유, 여러 상점 상품 일괄 등록은 제외한다. 최소 모집 인원 달성 조건도 없다.


## 2. 역할·사용 환경·권한

| 역할 | 사용 환경 | 허용 범위 |
| --- | --- | --- |
| 비회원 | 구매자 앱 | 공개 상점·공구 상품 조회 |
| 구매자 | Capacitor 앱 | 본인 정보·저장 상점·예약·알림·신고 관리 |
| 판매자 | PC·모바일 반응형 웹 | 본인 소유 상점과 그 상점의 공구·예약 관리 |
| 플랫폼 관리자 | 운영 웹 화면 | 신고 조회, 상품 숨김, 상점 제한·해제, 조치 이력 |

- 구매자·판매자는 같은 카카오 계정과 회원 시스템을 사용한다. 상점 최초 등록 성공 시 판매자 역할을 부여한다.
- 구매자와 판매자 역할을 함께 가질 수 있다. 역할별 화면 진입만으로 서버 권한이 부여되지 않는다.
- 운영자 권한은 일반 회원이 선택하거나 상점 등록으로 얻을 수 없다. 운영 권한 부여 방식은 기술·운영 설정으로 관리한다.
- 서버는 모든 요청의 회원, 대상 예약 소유권, 대상 상점 소유권을 검증한다. 화면에서 넘긴 sellerId·buyerId만 신뢰하지 않는다.
- 판매자 상점 전환은 조회 범위 선택이다. 다른 판매자의 storeId를 보내도 조회·변경할 수 없다.
- 운영자 외에는 신고자의 정보나 다른 판매자의 예약 명단을 조회할 수 없다.


## 4. 공통 데이터·입력 기준

### 4.1 주요 데이터

| 데이터 | 주요 항목 |
| --- | --- |
| 회원 | 회원 ID, 카카오 연결 식별자, 역할, 이름, 연락처, 동의 이력, 알림 설정, 탈퇴 상태 |
| 상점 | ID, 소유 회원, 이름, 주소·상세주소, 연락처, 소개, 운영시간, 정상·제한·폐점 표시 |
| 저장 상점 | 회원 ID, 상점 ID, 저장 시각, 기본 상점 여부 |
| 공구 상품 | ID, 상점 ID, 상품명, 이미지, 설명, 판매 단위, 원화 단가, 총 수량, 선택적 1인 한도, 접수 일정, 픽업 날짜, 당일 마감, 취소 제한, 공개·숨김 여부 |
| 예약 | ID, 표시용 예약번호, 회원·상점·공구 ID, 수량, 픽업일, 예약 당시 단가·정책·예약자·픽업 정보, 예약·결제 상태, 변경 버전 |
| 이력 | 대상 ID, 처리자, 행동, 변경 전후 값, 사유, 처리 시각 |
| 알림 | 수신 회원, 예약 ID, 목적, 일정 버전, 예정·발송 시각, 전달 결과, 읽음 여부 |
| 신고·요청 | 작성 회원, 대상, 유형, 내용, 접수·처리 상태, 처리 사유·시각 |

DB 스키마를 확정하는 표가 아니다. 화면과 처리에 필요한 논리 정보다. 공구 게시물과 독립 상품 카탈로그 분리는 필수가 아니다.

### 4.2 구현 기본안

| 입력 | 기본 검증안 |
| --- | --- |
| 이름 | 공백 제외 필수, 앞뒤 공백 제거, 1~50자 |
| 상점명·상품명 | 필수, 1~100자 |
| 연락처 | 직접 입력, 공백·하이픈 정규화 후 전화번호 형식 검증. 인증 완료 표시 금지 |
| 주소 | 도로명 또는 지번 주소·상세주소. 주소 선택 도구 미정, 직접 입력 가능 |
| 가격 | 원화 정수, 1원 이상. 부동소수 계산 사용 금지 |
| 총 수량·예약 수량 | 1 이상 정수 |
| 1인 최대 수량 | 미설정(null) 또는 1 이상 정수. 미설정은 개인 한도만 없음 |
| 이미지 | 대표 1장 필수, 상세 선택. 기본안 JPEG·PNG·WebP, 파일당 10MB 이하, 상세 10장 이하 |
| 상세 설명 | 필수, 기본안 1~10,000자. 임의 스크립트 실행 불가 |
| 사유·신고 내용 | 공백 제외 필수, 기본안 1~1,000자 |
| 운영시간 | 시작 < 종료, 기본안 동일 날짜 내 시간. 자정 넘김 운영은 별도 설계 |

- 프론트엔드와 서버가 같은 검증을 수행하되 서버 판단이 최종이다.
- 작성 중 저장은 필수 항목 미완성도 허용할 수 있지만 공개 시 모든 필수 조건을 검증한다.
- 업로드 실패 시 이미 저장된 내용·이미지를 잃지 않는다. 서버에서 형식·크기도 재검증한다.
- 오류는 해당 입력 옆에 표시하고 수정 가능하게 한다. 내부 식별자나 서버 오류 전문을 노출하지 않는다.


## 11. 날짜·수량·상태 공통 규칙

### 11.1 시간 경계

- 표시·사업 정책 기준은 Asia/Seoul, 서버 검증 기준 시각 사용.
- 변경·직접 취소 허용: 현재 시각 < 기존 픽업일 00:00. ‘전날 23:59까지’는 23:59:59까지를 포함하고 당일 00:00부터 차단하는 구현 표현이다.
- 신규 접수 기본안: 시작 ≤ 현재 < 전체 예약 마감. 당일은 현재 < 해당 날짜 당일 접수 마감도 만족.
- 마감 시각에 도달한 요청은 실패. 화면을 마감 전에 열었어도 처리 시각이 마감 이후면 실패한다.
- 날짜 변경은 기존·새 픽업일 모두 오늘보다 미래. 접수 중단이더라도 유효 날짜로 변경 가능.

### 11.2 수량 산식

```text
총 점유 수량 = 예약 확정 + 픽업 완료 + 미수령 상태의 수량 합계
남은 수량 = 공구 총 수량 - 총 점유 수량
개인 한도 사용량 = 같은 구매자·공구의 취소되지 않은 수량 합계
준비 수량 = 선택한 픽업일의 예약 확정 수량 합계
예상 금액 = 예약 당시 정수 단가 × 예약 수량
```

- 취소만 점유 반환. 픽업·미수령은 판매 또는 확보된 수량이므로 반환 없음.
- 감소는 감소분 반환. 날짜 변경은 전체 점유 불변.
- 기존 예약 변경 시 기존 수량을 중복 합산하지 않는다.
- 미수령 후 재예약은 원문에 금지로 확정되지 않았으므로 기본안은 잔여·개인 누적 한도·접수 조건 내 허용하되 종료 이력 보존. 이 세부 적용은 구현 설계에서 확인한다.

### 11.3 예약 상태 전이

| 현재 | 행동 | 결과 | 수량 |
| --- | --- | --- | --- |
| 없음 | 생성 | 예약 확정 | 확보 |
| 예약 확정 | 수량·날짜 변경 | 예약 확정 | 차이만 반영 |
| 예약 확정 | 구매자 취소 | 구매자 취소 | 반환 |
| 예약 확정 | 판매자 개별·공구 취소 | 판매자 취소 | 반환 |
| 예약 확정 | 전달 기록 | 픽업 완료 | 유지 |
| 예약 확정 | 미수령 기록 | 미수령 | 유지 |
| 픽업 완료 | 오기록 정정 | 예약 확정 | 유지 |

취소 상태→예약 확정 복구 없음. 미수령→예약 확정 자동 복구 없음. 결제 상태 전이는 별도이며 미결제↔현장 결제 완료 중 역방향은 사유 있는 정정만 허용한다.

### 11.4 공구·접근 상태

- 작성 중, 예약 예정, 예약 중, 접수 중단, 마감, 공구 취소는 공구 접수 상태.
- 숨김과 상점 이용 제한은 운영 접근 상태이며 별도 공구 상태로 혼용하지 않는다.
- 시간 마감·수동 중단·숨김·제한이 동시에 있어도 예약 허용 조건을 모두 충족해야 한다.
- 접수 재개는 운영 숨김·상점 제한을 해제하지 않는다.

### 11.5 허용 행동 요약

| 조건 | 신규 | 증가 | 감소 | 날짜 변경 | 구매자 취소 |
| --- | --- | --- | --- | --- | --- |
| 접수 열림·전날 기한 내 | 조건 내 | 조건 내 | 제한 없으면 가능 | 유효 미래 날짜 | 제한 없으면 가능 |
| 중단·마감·전날 기한 내 | 불가 | 불가 | 제한 없으면 가능 | 유효 미래 날짜 | 제한 없으면 가능 |
| 직접 취소 제한 | 조건 내 | 조건 내 | 불가 | 기한 내 가능 | 불가 |
| 픽업 당일·경과 | 당일 접수 조건 내 | 불가 | 불가 | 불가 | 불가 |
| 예약 종료·공구 취소 | 별도 재예약 규칙 | 불가 | 불가 | 불가 | 불가 |

운영자 숨김·상점 제한에서 기존 예약 감소·날짜 변경을 허용하는 상세 범위는 구현 기본안으로 기존 약속 처리 경로를 유지하되 신규·증가는 차단한다. 운영자가 법정 처리 경로를 차단할 수 없다.


## 14. 오류·동시성·실패 복구

| 오류 예시 코드 | 화면 처리 |
| --- | --- |
| AUTH_REQUIRED | 로그인 안내·원래 화면 복귀 |
| FORBIDDEN / NOT_FOUND | 권한 없는 개인정보 노출 없이 접근 불가 |
| STORE_RESTRICTED / LISTING_HIDDEN | 신규 접수 불가, 기존 예약 안내 경로 |
| BOOKING_CLOSED / TODAY_CUTOFF | 접수 마감 안내·다른 날짜 확인 |
| QUANTITY_UNAVAILABLE | 최신 잔여 수량 갱신 |
| BUYER_LIMIT_EXCEEDED | 적용 한도 표시 |
| ACTIVE_RESERVATION_EXISTS | 기존 예약 이동 |
| REPURCHASE_NOT_ALLOWED | 같은 공구 픽업 완료 후 재구매 불가 |
| CHANGE_DEADLINE_PASSED | 당일 변경·취소 불가와 문의 표시 |
| CANCELLATION_RESTRICTED | 취소·감소 제한 안내 |
| INVALID_PICKUP_DATE | 유효 날짜 재선택 |
| VERSION_CONFLICT | 최신 상태 재조회·재확인 |
| REQUEST_PENDING | 처리 여부 조회, 새 요청 중복 실행 금지 |

코드는 API 설계 권장안이다. 사용자에게 그대로 보여주지 않는다.

- 예약 생성·수량 수정·취소·공구 취소·픽업 정정은 원자적 처리. 두 기기에서 동일 대상 수정 시 낙관적 버전 검증 또는 동등한 잠금 적용.
- 동일 요청 키 재시도는 기존 결과를 반환한다. 다른 내용으로 같은 키 사용 시 충돌 처리.
- 응답 유실 시 요청 키로 결과 확인. 확인 없이 ‘실패’로 판단해 새 예약 만들지 않는다.
- 취소·감소의 수량 반환은 정확히 한 번. 알림 실패가 예약 실패로 보이지 않게 한다.
- 목록·통계는 최신 상태를 반영하며 중요한 동작 실행 시 서버에서 다시 검증한다.
- 실패 메시지·재시도·빈 화면을 구분하고 입력 내용을 가능한 한 유지한다.

## 18. 세부 설계 인계 항목

확정 사업 정책과 별도로 다음 작업을 수행한다. 본 문서의 구현 기본안을 수용하거나 조정한 결과는 버전 이력에 남긴다.

- 이미지·문자 길이 제한, 주소 도구, 운영시간 캘린더·휴무·자정 넘김 설계
- 운영자 접근·인증·신고 처리 화면과 탈퇴 후 본인 확인·문의 경로
- 예약 있는 일정·장소 변경의 합의·재선택 UI, 미수령 이후 늦은 수령·재가입 동일인 처리
- 회원·공구·예약·이력·알림 데이터 모델 및 API 상세
- 결제 확인 후 픽업 완료 조건, 미수령 시점, 오기록 정정 범위의 구현 기본안 확인
- 출시 전 보존 의무 주체·필드·기산일, 약관·개인정보 처리방침 적용
- 향후 결제 방식과 수령 방식을 별도 필드로 확장하되 MVP는 현장 결제+픽업만 허용


## 공통 인증

### AUTH-01 카카오 로그인·가입 — B01/S01, P02·P15

**입력:** 카카오 로그인 결과, 최초 필수 동의, 이름·연락처.

**흐름:** 로그인 시작 → 카카오 인증 → 서버 검증 → 기존 회원 조회 → 신규 회원이면 필수 정보·동의 → 서비스 세션 발급 → 원래 요청 화면으로 복귀.

- 카카오 로그인 취소·실패 시 예약 생성이나 가입 완료로 처리하지 않는다.
- 기존 회원이면 새 계정을 중복 생성하지 않는다. 필수 프로필이 없으면 보완 화면으로 이동한다.
- 이메일·전화번호를 카카오에서 항상 받는다고 가정하지 않는다. 연락처는 직접 입력한다.
- 필수 동의 문구·버전·시각을 저장한다. 선택 동의는 필수 가입과 분리한다.
- 비회원이 예약·저장·신고를 선택하면 로그인 후 같은 대상 화면으로 돌아간다.
- 구매자 앱에 판매자 관리 모드를 구현하지 않는다. 판매자 웹에서 같은 계정으로 로그인할 수 있다.

**검수:** 같은 계정의 앱·웹 로그인은 같은 회원으로 연결되고, 로그인 실패 후 예약이 생기지 않는다.

## 13. 탈퇴·정보 처리 — ACCOUNT-01, B11, P16

1. 탈퇴 진입 시 본인 유효 예약·운영 상점·미완료 거래 목록 조회.
2. 거래 없음 → 영향 설명·확인 → 계정 탈퇴.
3. 거래 있음 → 허용 취소 또는 판매자·운영자 처리 요청 안내.
4. 해결되지 않았어도 요청을 무기한 거절하지 않는다. 거래 정보의 적법한 최소 보관과 계정 접근 종료를 분리 처리.
5. 판매자 탈퇴 시 소유 상점 신규 접수 중단, 기존 예약 자동 취소 없음. 이행·사유 취소 처리 경로 마련.
6. 세션·토큰·기기 푸시 연결 종료, 불필요 프로필·저장 상점 정보 파기.
7. 보존 대상 기록을 목적·기한·접근 권한에 따라 분리 보관, 종료 시 파기.

- 모든 개인정보를 일괄 5년 보관하지 않는다. 요구사항 3.3·3.4의 공식 근거와 실제 사업 역할 검토 결과로 필드·기산일을 정한다.
- 탈퇴 전 미완료 거래가 있음을 알리고, 탈퇴 후 문의 경로·본인 확인 방식 제공. 탈퇴 후 기존 앱 푸시 발송 금지.
- 기술 기본안: 거래 식별용 내부 참조는 보존 필요성에 따라 유지할 수 있으나 로그인 자격·일반 프로필과 분리. 회원 API에서 탈퇴 사용자의 일반 프로필 조회 차단.
- 재가입 시 이전 탈퇴 계정·예약을 임의로 복구하거나 개인 한도 우회 허용으로 가정하지 않는다. 법적 보관 범위 안의 동일인 처리 방법은 후속 설계다.
