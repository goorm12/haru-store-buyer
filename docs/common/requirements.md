# 하루상점 — 공통 요구사항·운영 정책

- 작성일: 2026-10-14
- 상태: 기존 예약 정책 확정 + 공지·문의 추가 요구사항 반영 (v1.1)
- 역할별 화면은 각 저장소의 요구사항 문서를 참조한다. 공통 사본은 두 저장소에서 동일하게 유지한다.
- 프로젝트명: 하루상점 (Haru Store)

## 1. 서비스 개요

판매자가 여러 상점을 등록하고 상점별 공동구매 상품과 예약을 관리한다. 구매자는 원하는 상점의 상품을 수량과 픽업일을 선택해 예약하고, 해당 상점에 방문해 결제·수령한다.

이 문서는 합의된 1차 MVP 기능과 운영 정책의 최종본이다. 세부 화면·기술 설계와 출시 전 법률 적용 검토는 별도 수행하며, 향후 온라인 결제·배송은 MVP 범위에 포함하지 않는다.

## 2. 확정 요구사항

### 2.1 서비스 범위와 관계

| 항목 | 요구사항 |
| --- | --- |
| 가입 | 카카오 로그인 기반 간편 가입 |
| 상점 운영 | 판매자 계정 하나로 여러 상점 등록·관리 |
| 상점별 관리 | 상품, 공구, 예약, 예약 가능 수량, 픽업 현황을 독립 관리 |
| 구매자의 상점 선택 | 여러 상점 저장·해제·전환 및 구매자가 기본 상점 지정 |
| 예약 | 상품 하나에 수량과 픽업일을 지정하고 즉시 확정 |
| 결제 | 방문 시 현장 결제 |
| 픽업 | 예약한 상점의 픽업 운영시간 내 수령 |
| 알림 | 예약 완료·변경·취소 안내 및 픽업 안내 |
| 제공 형태 | 구매자용 Capacitor 앱, 판매자용 PC·모바일 반응형 웹. 같은 카카오 계정·회원 시스템·서버를 사용하고 역할별 화면과 권한 구분 |

- 판매자와 상점은 1:N 관계다.
- 모든 상품과 예약은 특정 상점에 소속된다.
- 동일 상품을 다른 상점에서 판매하거나 다음 공구를 진행하면 별도로 등록한다.
- 첫 버전 제외: 온라인 결제, 배송, 장바구니, 리뷰, 쿠폰, 상품 옵션, 지점 간 재고 공유, 여러 지점 상품 일괄 등록, 직원 초대.

### 2.2 사용자와 권한

| 사용자 | 권한 |
| --- | --- |
| 비회원 | 상점 및 상품 목록·상세 조회 |
| 플랫폼 관리자 | 신고 조회, 상품 숨김, 상점 이용 제한·해제 및 조치 이력 관리 |
| 구매자 | 내 상점 저장, 본인 예약 생성·조회·변경·취소 |
| 판매자 | 본인 소유 상점 등록·관리, 해당 상점의 상품·예약·픽업 관리 |

구매자·판매자는 같은 카카오 계정으로 로그인한다. 상점 등록 시 판매자 역할을 부여하며 같은 계정으로 구매자 역할도 이용할 수 있다. 판매자 앱 모드는 후속 범위다.

판매자 가입·상점 개설은 사전 운영자 승인 없이 가능하다. 상점명·주소·연락처·픽업 운영시간 등 필수 정보 입력 후 운영한다. 구매자의 상점·상품 신고와 플랫폼 관리자의 신고 조회·상품 숨김·상점 이용 제한·해제 기능을 MVP에 포함한다. 조치 사유와 처리 이력을 보존하며 제한된 상점은 신규 접수를 차단한다. 기존 예약은 자동 취소하지 않고 처리·문의 경로를 유지한다.

상품 조회에는 로그인이 필요하지 않다. 예약, 내 예약 조회, 상점 저장에는 로그인이 필요하다. 서버에서 본인 예약 여부와 상점 소유권을 검증한다.

### 2.5 공구 등록 정보

| 구분 | 항목 |
| --- | --- |
| 소속 | 판매·픽업할 상점 |
| 상품 | 상품명, 대표 이미지, 상세 설명, 선택 입력인 상세 이미지 |
| 판매 | 판매 단위, 단위당 가격, 전체 예약 가능 수량, 선택 입력인 1인 최대 수량 |
| 예약 일정 | 예약 시작 일시, 예약 마감 일시 |
| 픽업 일정 | 픽업 가능 날짜 목록, 당일 접수 마감 기준 |
| 변경·취소 | 전날 23:59 마감, 공구별 구매자 직접 취소 제한 여부 |
| 픽업 안내 | 상점 주소·운영시간, 추가 안내 |

판매 단위가 1박스이면 수량 2는 2박스를 의미한다. 날짜별 수량 한도와 시간대별 예약은 첫 버전에서 지원하지 않는다.

### 2.6 예약 정책

- 판매자 승인 없이 즉시 확정한다.
- 최소 수량은 판매 단위 기준 1개다.
- 수량·픽업일 변경은 전날까지 허용하고 당일에는 불가하다. 마감은 기존 픽업일 전날 23:59(한국 시간)이며 당일 00:00부터 제한한다. 직접 취소 제한 공구는 수량 감소·전체 취소도 막는다.
- 공구 상품 전체 수량 한도로 관리한다.
- 구매자별 최대 수량은 기본적으로 제한하지 않는다. 공구 상품에 1인 최대 수량을 설정하면 해당 한도를 적용한다. 무제한은 전체 잔여 수량 한도를 없앤다는 뜻이 아니다.
- 같은 구매자는 같은 공구 상품에 유효 예약을 하나만 유지한다. 추가 구매는 기존 예약의 수량 변경으로 처리한다. 다른 날짜로 중복 예약하여 한도를 우회할 수 없다.
- 취소 후에는 접수 기간·픽업일·수량 조건을 만족하면 새로 예약할 수 있다. 픽업 완료 후 같은 공구의 재구매는 불가하다. 1인 한도는 취소된 수량을 제외한 예약 수량에 적용하며 미수령 수량은 한도에서 제외하지 않는다.
- 판매자는 오늘을 포함한 미래 날짜를 픽업 가능일로 지정할 수 있다.
- 구매자는 지정된 날짜 중 접수 가능한 날짜만 선택한다.
- 당일 픽업은 오늘이 픽업 가능일이고 판매자가 공구에 설정한 당일 접수 마감 전일 때 가능하다. 공구 전체 예약 마감도 함께 적용한다.
- 별도 시간대 선택 없이 상점 픽업 운영시간 내 방문한다.
- 예약 기간, 접수 상태, 남은 수량, 픽업일의 접수 마감을 서버에서 검증한다.
- 예약 당시 단가와 예약자 이름·연락처를 저장한다. 상품 가격 변경은 기존 예약 단가에 영향을 주지 않는다.
- 예상 결제 금액은 예약 당시 단가 × 수량이다.
- 동시에 여러 예약이 들어와도 수량 한도를 초과할 수 없다.
- 반복 클릭·통신 재시도로 같은 예약이 중복 생성되지 않아야 한다.
- 다른 상점으로 예약을 변경할 수 없다. 다른 상점 이용 시 취소 후 새로 예약한다.

### 2.7 변경·취소 정책

| 행동 | 확정된 처리 원칙 |
| --- | --- |
| 수량 증가 | 변경 기한 내, 접수가 열려 있고 남은 수량이 있을 때 허용 |
| 수량 감소 | 직접 취소 제한이 없는 공구에서 전날 23:59까지 최소 1개로 변경 가능 |
| 픽업일 변경 | 기존 날짜와 새 날짜 모두 당일이 아니고 전날 변경 기한 내일 때 유효 픽업일로 변경. 신규 접수 마감과는 별개 |
| 구매자 취소 | 공구의 직접 취소 정책과 취소 기한이 허용하는 경우 전체 예약 취소 |
| 취소 수량 | 해당 공구의 예약 가능 수량에 반환 |
| 취소 복구 | 복구 기능 없이 새 예약 |
| 마감 후 요청 | 앱에서 변경·취소 제한, 상점 연락처 안내 |

변경 실패 시 기존 예약을 유지한다. 변경 전후 수량·픽업일, 처리 주체·시각을 저장한다. 변경·취소 마감은 기존 픽업일 전날 23:59다. 당일 변경·직접 취소는 불가하다. 당일 새로 예약한 건도 동일하다. 직접 취소 제한이 있어도 수량 증가·픽업일 변경은 각각의 조건과 기한 내 허용한다. 예약 당시 취소 정책을 저장하고 이후 정책 변경을 소급 적용하지 않는다.

### 2.8 접수 중단·공구 취소 정책

| 행동 | 결과 |
| --- | --- |
| 접수 중단 | 신규 예약·수량 증가 차단, 기존 예약 유지 |
| 접수 재개 | 예약 기간과 남은 수량이 유효하면 재개 |
| 예약 마감 | 신규 예약·수량 증가 차단 |
| 공구 전체 취소 | 아직 픽업하지 않은 유효 예약 취소, 구매자 안내 |

- 접수 중단·마감 후에도 공구에 적용된 변경·취소 정책이 허용하는 경우 수량 감소·구매자 취소를 허용한다.
- 접수 중단·마감 후에도 기존 예약은 변경 기한 내 유효한 픽업일로 변경할 수 있다. 당일에는 변경할 수 없다. 여기서 유효 픽업일은 공구가 유지하는 날짜이며, 신규 접수 가능 여부와 구분한다.
- 공구 취소는 사유 입력이 필수이며, 픽업 완료된 예약은 취소하지 않는다.
- 판매자는 특정 유효 예약을 개별 취소할 수 있다. 사유 입력, 구매자 알림, 처리 이력 저장, 수량 반환을 수행한다. 이미 취소되었거나 픽업 완료·미수령 처리된 예약은 대상에서 제외한다.
- 모든 처리는 해당 상점의 공구·예약에만 적용한다.
- 예약이 있는 공구는 삭제하지 않고 이력을 보존한다.
- 예약이 있는 공구도 수정할 수 있다. 기존 예약의 가격·수량·픽업 약속을 임의로 덮어쓰지 않으며, 기존 예약 단가를 유지하고 총 수량은 점유 수량 아래로 줄일 수 없다. 예약이 있는 픽업일 삭제·장소 변경은 기존 예약을 일괄 덮어쓰지 않고 별도 처리와 구매자 안내를 거친다. 구체적인 동의·일정 재선택 화면은 후속 설계한다.

### 2.9 픽업·현장 결제 정책

- 예약번호 또는 이름·연락처로 예약을 확인한다.
- 현장 결제를 기록하고 상품 전달 후 픽업 완료 처리한다.
- 픽업 완료된 예약은 구매자가 변경·취소할 수 없다.
- 픽업일이 지난 유효 예약에는 픽업일 경과 표시를 한다.
- 판매자가 실제 상황을 확인한 뒤 미수령 처리한다.
- 미수령 예약을 자동 취소하거나 수량을 자동 반환하지 않는다.
- 결제 여부와 예약 상태를 별도로 저장한다.
- 앱은 현장 결제 기록만 관리하며 결제 승인·환불은 처리하지 않는다.
- 판매자가 잘못 입력한 픽업 완료·현장 결제 기록을 정정할 수 있다. 사유를 필수 입력하고 변경 전후 상태, 처리자, 시각을 남긴다. 두 기록은 각각 정정하며 실제 돈의 환불·재결제를 수행하지 않는다.

### 2.10 상태 정의

| 대상 | 상태 |
| --- | --- |
| 공구 상품 | 작성 중, 예약 예정, 예약 중, 접수 중단, 마감, 공구 취소 |
| 예약 | 예약 확정, 구매자 취소, 판매자 취소, 픽업 완료, 미수령 |
| 결제 | 미결제, 현장 결제 완료 |

픽업일 경과는 날짜로 계산하는 표시이며 자동 미수령 처리를 의미하지 않는다. 수량·날짜 변경은 별도 상태 없이 이력으로 관리한다.

### 2.11 알림

| 발생 시점 | 안내 내용 |
| --- | --- |
| 예약 확정 | 상점, 상품, 수량, 금액, 픽업일 |
| 예약 변경 | 변경된 수량·픽업일 |
| 예약 취소 | 취소 완료 |
| 픽업 전날 | 다음 날 픽업 예정, 장소·운영시간 |
| 픽업 당일 | 당일 픽업 안내 |
| 공구 취소 | 취소 사유와 예약 정보 |

- 서버가 최신 예약 상태를 확인해 푸시를 발송한다.
- 취소·픽업 완료 예약에 픽업 알림을 보내지 않는다.
- 픽업일 변경 시 예정 알림을 갱신한다.
- 같은 목적의 알림을 중복 발송하지 않는다.
- 발송 시각이 지난 알림은 소급 발송하지 않는다.
- 알림 선택 시 해당 예약 상세로 이동한다.
- 푸시 권한이 없어도 앱의 알림 내역에서 안내를 확인할 수 있다.
- 전날 오후 6시에 1회, 당일 픽업 시작 2시간 전에 1회 안내한다. 기준은 구매자별 약속 시간이 아니라 해당 픽업일의 상점 운영 시작 시각이다.
- 당일 계산 시각이 오전 8시 이전이면 오전 8시로 조정한다. 조정한 시각에 이미 픽업이 시작되었거나 시작 시각과 같으면 해당 알림은 생략한다.
- 예: 오전 10시 시작 → 전날 18시·당일 08시. 오전 9시 시작 → 당일 08시. 오전 8시 이전 또는 8시 시작 → 당일 사전 알림 생략.
- 미수령·취소·픽업 완료 상태에는 예정 픽업 알림을 발송하지 않는다. 이미 지난 시각의 알림은 예약 완료 안내로 대체하며 소급 발송하지 않는다.

### 2.12 공통 처리

- 일정은 한국 시간 기준으로 처리한다.
- 권한, 상점 소속, 예약 가능 여부, 수량은 서버에서 검증한다.
- 예약 가격과 상태·변경 이력을 보존한다.
- 통신 결과가 불명확하면 기존 예약 생성 여부를 확인한 후 재시도한다.
- 개인정보는 예약 운영에 필요한 범위로 수집한다.
- 회원 탈퇴는 3.3의 거래 정리·정보 파기·분리 보관 정책을 적용한다.

### 3.1 변경·취소 상세

- 기존 픽업일 전날 23:59까지 처리하며 당일 00:00부터 변경·직접 취소를 막는다.
- 직접 취소 제한 상품은 전체 취소와 수량 감소를 모두 막는다. 수량 증가·픽업일 변경은 기한과 조건을 만족하면 허용한다.
- 정책은 예약 시 고지하고 예약에 저장한다. 기존 예약에 변경된 취소 정책을 소급 적용하지 않는다.
- 직접 취소 제한은 앱 기능 정책이며 법정 청약철회·해제·하자 구제 권리를 배제하지 않는다. 문의 접수·법정 요청 처리 경로를 제공한다.
- 판매자의 공급 불가 등으로 취소하는 것은 구매자 직접 취소 제한과 별개다.
- 현장 결제라고 통신판매 관련 규정이 자동 제외되는 것으로 가정하지 않는다. 실제 계약 구조에 대한 출시 전 검토를 수행한다.

### 3.2 알림 상세

- 구매자별 시간 예약 없이 해당 날짜의 픽업 운영 시작 시각을 사용한다.
- 전날 18시와 당일 시작 2시간 전 발송. 당일 알림은 08시 이전이면 08시로 조정한다.
- 조정 시각에 픽업이 시작됐거나 시작 시각과 같으면 생략한다. 지난 알림 소급 발송 및 중복 발송은 하지 않는다.
- 날짜·운영시간 변경 시 재계산하고 발송 직전 최신 예약 상태를 확인한다.

### 3.3 탈퇴·정보 보관

- 미완료 거래가 없는 회원은 탈퇴 처리한다. 로그인 세션·인증 토큰·푸시 토큰을 무효화하고 불필요한 프로필·저장 상점 정보를 지체 없이 파기한다.
- 유효 예약이 있는 구매자에게 예약 목록과 처리 경로를 안내한다. 허용되는 예약은 취소할 수 있으며, 제한된 예약은 판매자·운영자에게 취소 또는 이행 처리 요청을 접수할 수 있다.
- 해결되지 않은 예약이 있어도 탈퇴·개인정보 요청을 무기한 거절하지 않는다. 계정 접근을 종료하고 거래 이행·분쟁 처리에 필요한 최소 정보만 적법한 근거와 기간으로 보관한다. 탈퇴 후 기존 푸시는 중단하고 필요한 거래 연락은 별도 적법한 근거로 처리한다.
- 판매자 탈퇴 요청 시 소유 상점의 신규 예약을 중단한다. 미완료 예약의 이행 또는 사유를 남기는 취소 처리 경로를 안내하고 처리 이력을 보존한다. 정산은 후속 결제 단계에서 별도로 정의한다.
- 법정 보존 기록은 일반 회원 정보와 분리 저장하고 접근 권한·파기 시점을 관리한다. 모든 회원 정보를 일괄 5년 보관하지 않는다.
- 전자상거래법 적용 시 계약·청약철회 기록 5년, 대금결제·재화 공급 기록 5년, 불만·분쟁 기록 3년, 표시·광고 기록 6개월을 적용한다. 출시 전 실제 사업 역할에 맞는 의무 주체·대상 필드·기산일을 확인하여 개인정보 처리방침과 보존 정책에 반영한다.
- 보존 근거가 없는 정보와 보존 기간이 끝난 정보는 파기한다. 통계가 필요하면 개인을 식별할 수 없는 형태로 처리한다.

## 4. MVP 완료 기준

1. 판매자가 여러 상점을 등록하고 전환해 관리한다.
2. 상점마다 상품·수량·예약 일정·픽업 가능일을 등록한다.
3. 구매자가 상점을 선택하고 수량·픽업일을 지정해 예약한다.
4. 구매자가 확정된 정책에 따라 예약을 변경·취소한다.
5. 판매자가 상점별·픽업일별 준비 수량과 예약자를 확인한다.
6. 예약 상태에 맞는 예약·픽업·취소 알림을 확인할 수 있다.
7. 판매자가 현장 결제와 픽업 완료·미수령을 기록한다.
8. 상점 간 데이터가 섞이지 않고 동시 예약에도 수량 한도를 지킨다.

## 6. 향후 확장 방향 — MVP 제외

- 동네 판매자뿐 아니라 인플루언서도 판매자로 참여하여 자신의 상점을 운영한다.
- 상점은 판매자의 판매 공간이다. 물리적 매장과 동일한 개념으로 제한하지 않는다.
- MVP의 모든 예약은 상점에서 현장 결제·픽업한다. 온라인 결제와 배송은 후속 단계에서 검토한다.
- 온라인 결제 도입 시 거래 당사자, PG 계약, 판매자 정산, 플랫폼 수수료, 취소·환불 책임을 결정한다.
- 인플루언서·판매자의 입점 자격, 본인·사업자 확인, 상품 공급 및 배송 책임은 후속 요구사항으로 정한다.
- 다른 플랫폼 상품을 취급하는 방식과 외부 플랫폼 연동은 확정하지 않았다.
- 지점은 실제 운영 형태를 설명할 때만 사용한다. MVP의 데이터 관리 단위는 상점이다.

## 7. 용어 기준

화면, 요구사항, API 설명에서 같은 개념을 같은 용어로 표현한다. 세부 정의와 영문 식별자 권장안은 [하루상점 용어 정의](./glossary.md)를 따른다.

- 가게 → 상점
- 사장님 → 판매자
- 손님 → 구매자
- 상품 조회·예약 → 공구 상품 조회·예약
- 주문 → MVP에서는 예약. 온라인 결제 도입 시 주문을 별도로 정의한다.
- 관리자 → 플랫폼 관리자. 판매자 화면은 판매자 관리 화면으로 부른다.

## 8. 거래 방식 확장 계획

| 단계 | 결제 방식 | 수령 방식 | 범위 |
| --- | --- | --- | --- |
| 1 | 현장 결제 | 픽업 | 현재 MVP |
| 2 | 온라인 결제 | 픽업 | 향후 |
| 3 | 온라인 결제 | 배송 | 향후 |

결제 방식과 수령 방식은 독립된 개념으로 설계하고 위 세 조합만 지원하도록 검증한다. 현장 결제+배송은 현재 계획에 없다. 공구가 지원할 방식과 구매자가 선택한 방식을 거래에 기록한다. 온라인 결제 상태와 픽업·배송 이행 상태도 별도로 관리한다.

향후에는 주문, 결제, 배송지, 배송비, 출고·송장, 환불, 정산, 판매 수수료 정책이 추가된다. 상점 하나를 현장형 또는 배송형으로 영구 고정하지 않는 방향으로 설계한다. 하나의 공구에서 여러 방식을 동시에 제공할지, 재고를 어떻게 공유할지, 판매자 확인 수준은 후속 결정 사항이다.




## 9. 후속 설계·출시 준비 항목

이 목록은 P01~P16을 다시 미결정으로 만드는 항목이 아니라, 확정 정책을 구현·운영하기 위한 작업이다.

- 화면 흐름, 데이터 모델, API, 플랫폼 관리자 권한 및 접근 방식 설계
- 예약된 픽업 날짜·장소 변경 시 안내·재선택·취소 처리 화면 설계
- 탈퇴 후 미완료 거래 문의 경로 및 법령별 보존 필드·기산일 검토
- 상표·도메인, 이용약관, 개인정보 처리방침 및 출시 전 법률 적용 확인
- 온라인 결제·배송·정산·환불은 후속 버전에서 별도 요구사항 수립

## 10. 상점 공지·문의 추가 범위

공통 정책 변경은 두 사본을 함께 수정하고 비교한다. 판매자·관리자 기능 구현 문서는 구매자 프로젝트에 포함하지 않는다. 공통 정책에 상대 역할의 행동이 등장하는 것은 거래 계약 설명이며 해당 화면 구현을 의미하지 않는다.

## 브랜치 흐름

develop → codex/작업명 → PR 대상 develop → 검토·병합. 배포 시 develop → main PR. 문서 작업은 main에 직접 적용하지 않는다.
